# 研究：作业演示数据与双身份浏览器验收

- 查询：如何用可重跑、不会覆盖原业务的假数据，让管理员与拍手直接检查发布、报单、多快递到货、凭证及结算。
- 范围：仓库内部代码与历史验收记录；只读研究，没有写数据库、调用变更接口、启动服务或打开浏览器。
- 日期：2026-10-29。

## 结论

建议用一个明确标记“演示”的店铺、一个管理账号与两个独立拍手账号，创建两项开放作业、一项带既有订单的关闭作业，以及至少六张订单，覆盖0/N、部分到货、全部到货和已结算。所有到货由正常Sync v2入库产生，结算通过管理接口确认，不直接写状态或结算表。

历史记录将10003标为专用演示店，但本次没有读取运行数据库，不能保证其现有内容仍全部为假数据。实施者先核对店名、管理资格与现有数据；只追加带本轮前缀的数据，不覆盖、不重置已有账号。若无法确认10003仍适合演示，创建新演示店，让服务器分配新的数字编号，不硬占10003。

## 正常接口顺序与精确请求

所有以下请求均以 `/api` 为前缀。管理请求需要 `Authorization: Bearer <管理token>` 和 `X-Active-Shop-ID: <店铺内部UUID>`；拍手请求只用拍手Bearer，不能携带管理令牌或伪造shop/owner字段。

### 1. 确认或创建演示店

管理登录：`POST /auth/login`，`{username,password}`；`GET /shops/my-shops`核对数字号与内部UUID、名称、角色和APPROVED状态。

如新建独立店：`POST /shops/create`，`{"name":"作业流程体验店（20261029演示）"}`。返回`{id,shop_number,name,created_at}`，后续管理头用id、拍手入口用shop_number，不能相互替代。

若不用既有管理员，可按现有 `POST /auth/register` 注册全新且专门命名的演示管理账号，字段 `{username,password,email?,phone?}`，再自己创建店铺。不要重置admin或任何旧账号。密码只用于本地演示，清单不保存令牌。

### 2. 作业照片与发布

`POST /jobs/media`：multipart字段 `file`，响应`{sha256,size,content_type}`。上传有效JPEG、PNG或WebP，单张不超过15MiB。

`POST /jobs`：

```json
{
  "title": "UX29-20261029-生活用品演示",
  "description": "仅用于本地流程验收，所有订单、快递和凭证均为假数据。",
  "cost_amount": "29.90",
  "refund_amount": "35.00",
  "status": "open",
  "photo_sha256s": ["<刚上传的64位摘要>"]
}
```

### 3. 拍手注册及多快递报单

`POST /worker/register`：`{shop_number:"<实际数字号>",username:"ux29_worker_a",password:"<专用演示密码>",display_name:"演示拍手甲",phone:""}`，乙同理。返回 `{token,worker}`。重跑时用 `POST /worker/login` 验证已有专用账号；同名但凭据/店铺不符则停止，不覆盖密码。

`POST /worker/orders`：

```json
{
  "job_id": "<实际作业UUID>",
  "order_number": "UX29-A-002",
  "tracking_numbers": ["UX29-20261029-T003", "UX29-20261029-T004", "UX29-20261029-T005"],
  "operation_id": "ux29:v1:order:a:002"
}
```

每单1～20个不同快递号，保留字母/前导零。相同拍手、相同作业中的订单号唯一；不同拍手可以同订单号，但演示主矩阵先使用明显不同号码便于检查隔离。

关闭作业示例必须先给甲创建订单，再 `PATCH /jobs/{job_id}` 发送完整作业字段、`status:"closed"`及 `expected_version`。不能先关闭再建单；不能指望未报过单的乙能看关闭作业。

### 4. 用真实同步生成到货

先 `POST /sync/v2/media`上传入库图片，multipart字段`file`，可带摘要字段`sha256`。也可复用同店已存在有效私有图片；不要跨店复用摘要引用。

`POST /sync/v2/push`：

```json
{
  "device_id": "jobs-ux-demo-20261029",
  "operations": [{
    "operation_id": "ux29:v1:inbound:t006",
    "kind": "inbound",
    "id": "UX29-IN-T006",
    "base_revision": 0,
    "data": {
      "tracking_number": "UX29-20261029-T006",
      "created_at": "2026-10-29T10:00:00+08:00",
      "ocr_status": "confirmed",
      "is_settled": false,
      "image_sha256": "<本店已上传图片摘要>",
      "items": [{
        "id": "UX29-IN-T006-L01",
        "product_code": "UX29-SKU-01",
        "product_name": "演示洗衣液",
        "quantity": 2,
        "purchase_price": "10.00",
        "sale_price": "12.50"
      }]
    }
  }]
}
```

HTTP200不等于每项成功，必须逐项检查`results[].status`为`applied`或`duplicate`；`conflict`应停止并给出原因。每个商品行id必须包含所属入库单，不能因为同一SKU就在不同单据复用行id；商品编码可复用来检查汇总。不要为造到货直接ORM插入InboundReceipt/stock，否则失去同步/库存真实链路证据。

### 5. 正常确认结算

`GET /jobs/orders/{order_id}`，只有所有快递都有当前有效receipt时提交：

```json
{
  "expected_version": 1,
  "expected_job_version": 1,
  "operation_id": "ux29:v1:settle:a003",
  "evidence": [{
    "tracking_number": "UX29-20261029-T008",
    "receipt_id": "<该快递receipt.receipt_id>",
    "revision": 1
  }, {
    "tracking_number": "UX29-20261029-T009",
    "receipt_id": "<第二个快递receipt.receipt_id>",
    "revision": 1
  }]
}
```

路径为`POST /jobs/orders/{id}/settle`，evidence必须包含该订单每一个当前快递，不是仅第一个。示例中的版本1仅展示JSON整数类型，实施脚本必须从刚读取的详情构造实际订单版本、作业版本与所有receipt修订值，不能硬编码1。返回后再GET管理员与拍手订单确认`settled`和金额；这只是结算记录，没有实际转账。

## 可重跑与隔离原则

建议后续实施一个明确命名的种子脚本/管理命令，默认只输出计划，显式参数选择目标演示店；脚本或本地manifest记录`dataset_version`、数字店号/UUID、演示账号名、每项作业/订单/图片/操作ID及原请求摘要，不记录Bearer。

1. 先读当前环境及店铺名，确认是专用演示环境；不得使用任何通配“首家店铺”。
2. 数据名称、订单号、单号、入库及行键都用本轮前缀。不要删除10003旧DEMO-ORDER-001或现有演示拍手。
3. 创建作业接口本身没有幂等键：重跑先按前缀查询并精确核对title/店铺，唯一匹配才复用；多项同名或配置冲突要停止，不能自动覆盖。仅凭标题无法完全证明归属，优先以本地manifest中的UUID核对。
4. 订单创建和结算用固定操作键、固定完整payload。`created_at`也固定；重跑不能在同一个operation_id下重新塞当前时间或新版本。
5. 管理员手工改过演示订单/价格之后，脚本应报告差异并退出或新建v2数据集，不把用户的验收操作“恢复原样”。
6. 结算重试保留最初完整payload，后台会先按操作键返回原结果；如果本地已丢该请求，不要复用同键配新version，先读取当前订单决定是否已经满足目标状态。
7. 不发送外部通知，不调用真实物流，不连真实支付，不重置用户密码。实际造数必须在后续实施授权阶段，当前研究不写数据库。

## 浏览器验收建议

管理员使用专用桌面会话，拍手甲/乙使用各自独立会话；不要复用用户正在看的默认tab。建议保留三个清楚命名的窗口：作业管理、订单核对、拍手甲（手机390宽）。乙可用于隔离断言后保留另一个窗口供切换检查。

现有入口：管理`/#/login`、`/#/shop/jobs`、`/#/shop/orders`；拍手`/#/worker/login?shop=<实际店号>`、`/#/worker/jobs`、`/#/worker/orders`。最终页面以Web优化实施后的真实路由为准。

验收顺序：管理员查看开放/关闭作业→拍手甲直接提交/补改→管理员搜索订单及任一快递，仍看到整订单所有快递和对应图→检查部分到货与全到→核对汇总再逐单结算→拍手刷新看到本人结算状态→甲尝试获取乙订单得到404、拍手令牌访问管理库存被拒。生产认证不能为演示绕过。

图片必须真实鉴权加载，不以数据库有摘要或API200代替图像已显示。手机宽360/390分别检查键盘/粘贴/长号/保存动作、无横向溢出；管理员桌面检查图片放大、商品及原快照。

## 后续责任边界

- 种子/数据实施者：可重跑脚本、专用照片、manifest、安全环境与目标店校验，不改业务状态算法。
- 主会话：检查/启动本地服务、实际造数、打开独立浏览器并保留给用户、记录实际URL/店号/账号和截图，不把历史地址直接当当前地址。
- Web实施者：操作入口/表单/核对呈现；先完成接口与路由后再做最终演示浏览器闭环。
- 检查者：重跑不重复、不覆盖、状态真实生成、跨人隔离、图片及快照授权；确认假数据只在演示店。
