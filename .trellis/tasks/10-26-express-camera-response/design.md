# Technical Design

## Architecture

重写 Android 极速模式的相机路径：项目自有 CameraX 会话同时绑定 Preview、ImageAnalysis（条码识别）和 ImageCapture（正式照片）。Flutter 极速页面承载项目自有原生预览，扫码锁定后停止分析提交但保留会话，切换为单据取景与快门；拍摄完成、可靠落盘及 pending 建单确认后恢复分析。退出页面才释放会话。普通入库保持原调用合同，若修改共享相机反馈/处理服务，必须回归普通入口。

使用项目已有 CameraX/ML Kit 版本对齐并显式声明所用依赖，不修改 pub-cache 或依赖插件源码。不能使用 mobile_scanner 的 returnImage 作为单据照片；不能同时启动两套相机占用硬件。CameraX 三用例绑定兼容性需要实现时探测并记录，失败时显示可恢复错误或安全退回现有相机路径，不静默降低清晰度。

## Capture State and Bridge

状态为 initializing → scanning → trackingLocked → capturing → captured/savingReceipt → scanning；失败进入可重试状态，disposed 后忽略旧回调。每个会话和 capture 使用唯一标识，将 trackingNumber、照片路径、裁剪坐标、方向绑定为一次不可变结果。快门按下只反馈“正在拍摄，请保持稳定”。保存完成回调才允许“已拍下，可以移开”；单据建成另外反馈“已录入”，不能混淆。

Flutter/native 桥接置于 src/platform，负载解析不进入 widget。原生只负责相机、条码、保存与事件，Flutter/data 仍拥有单据与库存。销毁、重试、前后台事件串行化；文件写完关闭后才发送成功。相机释放必须可 await，不能用固定延迟代替资源完成信号。

拍照态顶部使用固定信息区域显示“快递单号”及本次 capture 绑定的完整 trackingNumber。长单号换行展示，不以省略号隐藏，不与取景内容重叠。它与拍摄事件共享同一不可变捕获上下文，不能从会变化的扫码回调临时读取；拍摄、保存期间保持一致，取消或下一单时按状态清除/替换。

## Image and Processing Pipeline

先将正式 JPEG 持久化在 App 文档目录，然后事务建立 pending 单据。保存失败不建成功单；建单失败保留重试上下文或清理未引用文件。收到建单确认才允许下一单，避免单号/照片错配。

将裁剪与 OCR 移出快门关键路径，使用有界串行工作队列；基于原始照片仅解码一次，保留正确方向，以 JPEG 输出并保持扩展名一致。裁剪几何必须来自实际预览变换而非假设 BoxFit.cover。原始照片在替代文件完整落盘并更新引用前不能删除；失败保留原照和可恢复状态。持久化 pending 单据是中断恢复依据；恢复任务必须检查单据仍存在、当前任务版本仍有效，不能让旧任务覆盖用户修改或重试结果。

连续采集期间仅刷新最近单据及局部状态；完整库存和历史刷新合并到退出极速模式或空闲时，避免每单 N+1 历史读取。OCR 与图片处理串行/限流，避免无界并发争抢相机资源。

## Compatibility and Risks

不迁移现有业务数据，不改变备份合同、OCR 引擎或库存审核语义。已有极速 OCR 直接更新库存与 spec 的人工审核要求存在既有偏差，本任务不扩大该行为；检查报告注明该既有问题。

原生预览触摸映射、CameraX 三用例绑定、暗光曝光及摄像头重新获取是主要风险。首先真机计时，区分 UI 提示错误、真实拍摄延迟和拍后处理，不以动画掩盖硬件时间。快照预览不能冒充最终拍摄照片；无真实曝光事件时使用保守的文件保存完成事件。

## Rollback

相机桥接及极速入口独立封装，保留原有普通拍照合同；可退回已有极速入口而无需数据回滚。旧数据和 pending 照片均须保留。若需要发布 APK，按项目规则先递增版本并归档 releases/app-v<version>.apk，不将 debug 签名描述为生产签名。
